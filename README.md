## ส่วนที่ 1 — Technical Mastery & Scalability

### ข้อ 1: Smart & Stale Rider Assignment

> **โจทย์:** จงเขียนฟังก์ชัน assignRider(order, riders) เพื่อหา Rider ที่เหมาะสมที่สุด โดยมีเงื่อนไข:
> Distance: ใช้สูตร Haversine คำนวณระยะทางจาก Rider ถึงร้านอาหาร
> Stale Data Protection: ห้ามเลือก Rider ที่ไม่ได้อัปเดตพิกัดเกิน 2 นาที
> Tie-breaker: ถ้าระยะทางต่างกันไม่เกิน 500 เมตร ให้เลือกคนที่มี Rating สูงกว่า
> Edge Case: หากไม่มี Rider ในระยะ 5 กม. เลย ระบบควรทำอย่างไร? อธิบาย Logic การขยายรัศมีหรือ Fallback

* **แนวคิด:**
1. ถ้า Rider คนไหนไม่ได้ส่งพิกัดมาเกิน 2 นาที (ข้อมูลเก่า/Stale) ถือว่าเขาอาจจะเน็ตหลุดหรือไม่ได้สแตนด์บาย ตัดทิ้งทันที
2. คำนวณระยะทาง: ใช้สูตร Haversine หาทางที่สั้นที่สุด (ระยะทางเป็นเส้นตรงบนผิวโลก)
3. ถ้าระยะทางห่างกันไม่เกิน 500 เมตร ให้สิทธิ์คนที่มี Rating สูงกว่าได้งานไปก่อน

### ข้อ 3: Code Review — Inventory Race Condition

> **โจทย์:** จงแก้ไข Code ต่อไปนี้ที่ใช้ตัดสต็อกเมื่อมีการสั่งซื้อ: ระบุปัญหา N+1 Query, Race Condition (สต็อกติดลบ), และการขาด Transaction พร้อมเขียน Code ใหม่ที่ใช้ Atomic Update หรือ Pessimistic Locking

* **ปัญหาในโค้ดเดิม:** 
1. **N+1 Query:** โค้ดมีการรันคำสั่ง SELECT และ UPDATE ใน for loop ถ้าลูกค้าสั่ง 10 ชิ้น มันจะวิ่งไปหา Database 20 รอบ ทำให้ช้ามาก
2. **ขาด Transaction:** หากสินค้าชิ้นที่ 1 หักสต็อกผ่าน แต่ชิ้นที่ 2 สต็อกไม่พอ ระบบจะค้างเติ่ง โดยที่ชิ้นแรกถูกหักไปฟรีๆ แต่สร้างออเดอร์ไม่สำเร็จ ข้อมูลไม่สอดคล้องกัน (Inconsistent Data)
3. **Race Condition:** ถ้าลูกค้าสองคนกดซื้อสินค้าชิ้นสุดท้ายพร้อมกัน ดึงค่าสต็อกไปเห็นว่ามีของทั้งคู่ จากนั้นก็หักสต็อกตามกัน ทำให้สต็อกติดลบและเกิดการขายของเกินจริง (Overselling)

## ส่วนที่ 2 — System Design & Business Logic

### ข้อ 4: Real-time Live Tracking Architecture

> **โจทย์:** ออกแบบระบบที่รองรับการติดตาม Rider 2,000 คนพร้อมกัน โดยลูกค้า 10,000 คนต้องเห็นตำแหน่งขยับแบบ Real-time:
> Data Flow: จะใช้โปรโตคอลใดระหว่าง WebSocket, gRPC, หรือ MQTT เพราะเหตุใด?
> Storage Strategy: ตำแหน่งพิกัดที่เปลี่ยนทุก 2 วินาที ควรเก็บลง Database ประเภทใด (SQL / NoSQL / In-memory) เพื่อไม่ให้ Disk I/O เต็ม?

**1. Data Flow (การรับส่งข้อมูลพิกัด)**

ฝั่งไรเดอร์ ➔ ใช้ MQTT

เหตุผล: MQTT ถูกสร้างมาเพื่ออุปกรณ์ที่เคลื่อนที่อยู่ตลอดเวลา จุดเด่นคือ มันส่งข้อมูลน้อยมาก เวลาไรเดอร์ขี่รถแล้วเน็ตหลุด พอเน็ตกลับมาปุ๊บ มันจะต่อให้เองอัตโนมัติทันทีโดยที่แอปไม่ค้าง

ฝั่งลูกค้า ➔ ใช้ WebSocket

เหตุผล: WebSocket เนื่องจากลูกค้าเปิดดูผ่านแอปมือถือ ต้องเปิด WebSocket ทิ้งไว้ระหว่างเซิร์ฟเวอร์กับแอปของลูกค้า พอพิกัดไรเดอร์ขยับ เซิร์ฟเวอร์ก็บอกพิกัดใหม่ไปหาลูกค้าได้ทันที แผนที่บนจอลูกค้าก็จะขยับตาม

ทำไมไม่ใช้ gRPC? เพราะ gRPC มันเหมาะกับ Server-to-Server หรือระบบหลังบ้าน ไม่เหมาะเอามาใช้งานทั่วไปกับลูกค้าจำนวณมาก

**2. Storage Strategy (การเก็บข้อมูลป้องกัน Disk เต็ม)**

* ตำแหน่งพิกัดที่เปลี่ยนทุก 2 วินาที (Write-heavy) จะต้องเก็บลง **In-memory Database (เช่น Redis)** เพราะการทำงานบน RAM ทำให้เขียน/อ่านได้รวดเร็วระดับมิลลิวินาที (O(1)) ช่วยแก้ปัญหา Disk I/O Bottleneck ที่จะเกิดหากเขียนลง SQL/NoSQL โดยตรง

### ข้อ 5: Rush Hour Cancellation Crisis

> **โจทย์:** จาก Scenario ที่ Rider ยกเลิกงานสูงถึง 25% ในช่วง Rush Hour:
> Requirement: ออกแบบฟีเจอร์ Dynamic Incentive (โบนัสพิเศษรายพื้นที่) เพื่อดึงดูด Rider
> Data Modeling: ออกแบบ Schema ที่เก็บประวัติการยกเลิกงาน (Cancellation Log) เพื่อวิเคราะห์พฤติกรรมทุจริต (Fraud Detection)

**1. Requirement: Dynamic Incentive**

* ในช่วงที่เกิดการยกเลิกงานสูง (Rush Hour + ฝนตก) ระบบจะคำนวณพื้นที่ (Geofence) ที่มีปริมาณออเดอร์ค้างเยอะแต่ไรเดอร์น้อย จากนั้นจะคำนวณเพิ่มค่ารอบเป็นโบนัสพิเศษ เช่น "+20 บาทต่อออเดอร์" และยิง Notification เพื่อให้ไรเดอร์ในบริเวณใกล้เคียงให้เข้าไปรับงาน

**2. Data Modeling: Cancellation Log Schema**

* ออกแบบ Schema เก็บประวัติอย่างละเอียด รวมถึงข้อมูล Device เพื่อนำไปวิเคราะห์ Fraud Detection (เช่น จับพฤติกรรมใช้เครื่องเดียวกันปั่นกดยกเลิกงาน):

### ข้อ 6: AI-Powered Delivery Time Predictor

> **โจทย์:** เขียน Prompt เพื่อให้ AI คำนวณ ETA โดยใช้ข้อมูล: ระยะทาง, สภาพอากาศ (ฝนตก), และเวลาเตรียมอาหารของร้าน
> พร้อมระบุวิธีจัดการหาก AI ทำนายเวลาผิดพลาดอย่างรุนแรง เช่น บอกว่าถึงใน 5 นาที ทั้งที่ฝนตกหนักและร้านอยู่ไกล 10 กม.

**1. System Prompt สำหรับให้ AI คำนวณ ETA:**

```text
Role:
คุณคือระบบ AI สำหรับคำนวณเวลาจัดส่งอาหาร (ETA Predictor)

Task:
คำนวณเวลาจัดส่งทั้งหมดเป็น "นาที" โดยอ้างอิงจาก:

ระยะทาง
สภาพอากาศ
เวลาเตรียมอาหารของร้าน

Rules:

ความเร็วปกติของไรเดอร์ = 30 กม./ชม.
คิดเวลาเดินทางจากสูตร:
1 กม. = 2 นาที
หากฝนตกหนัก:
ลดความเร็วลง 50%
เวลาเตรียมอาหาร:
ร้านอาหารทั่วไป: ใช้ค่าที่รับเข้ามาโดยตรง
ร้าน Fast Food: ลดเวลาเตรียมลง 30%
ห้ามประเมินเวลาต่ำเกินจริง
หากระยะทางเกิน 8 กม. และฝนตกหนัก:
ETA ต้องไม่น้อยกว่า 30 นาที

```

**2. การจัดการกรณี AI ทำนายผิดพลาดรุนแรง (Hallucination)**

* สร้าง **(Rule-based)** ไว้ที่ฝั่ง Backend
* หากผลลัพธ์จาก AI ต่ำกว่าความเป็นจริง (เช่น ระยะทาง 10 กม. ฝนตกหนัก แต่บอกใช้เวลา 5 นาที) ระบบจะทำการ **Auto-Reject** ค่าของ AI ทันที และเปิดโหมด Fallback สลับไปใช้สูตรคำนวณระยะทาง (Standard Matrix) เพื่อความถูกต้องและปลอดภัย
